# ADR-001: Distributed Monolith вместо Microservices

**Дата:** 2026-03-01  
**Статус:** Accepted  
**Авторы:** CAT Team

---

## Контекст

CAT — SaaS-платформа для мониторинга онлайн-полки. На старте: 1-2 разработчика, MVP за 3-4 месяца, неопределённая нагрузка (10–50 клиентов на начало). Нужна скорость разработки, простой деплой и возможность вырасти.

## Рассматриваемые варианты

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| Microservices | Независимый скейл, fault isolation | Сложность DevOps, latency между сервисами, overhead на старте |
| Monolith (single process) | Простота | Нет изоляции между доменами, тяжело разделить позже |
| **Distributed Monolith (выбран)** | Чёткие границы доменов, один репо, простой деплой | Монолитный деплой (всё или ничего) |

## Решение

**Distributed Monolith в монорепо** — 4 независимых Docker-сервиса (`api`, `collector`, `processor`, `frontend`) с чёткими границами доменов, но единой кодовой базой и единым Docker Compose деплоем.

```
services/
├── api/        # FastAPI — HTTP, бизнес-логика, БД
├── collector/  # Celery workers — скрапинг
├── processor/  # ML pipeline — CLIP, ruBERT
└── frontend/   # React SPA
```

Межсервисное взаимодействие: через Redis (очереди Celery) и PostgreSQL. Нет HTTP-вызовов между сервисами.

## Последствия

- **Положительные:** деплой одной командой `docker compose up`, общий git-history, простое локальное развёртывание, нет latency между доменами
- **Отрицательные:** сервисы деплоятся вместе; если нужен независимый скейл коллектора — потребуется вынос в отдельный compose-стек
- **Путь к микросервисам:** границы уже выделены, при необходимости `collector` и `processor` извлекаются без рефакторинга
