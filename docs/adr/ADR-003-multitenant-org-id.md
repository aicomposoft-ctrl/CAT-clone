# ADR-003: Multi-tenant Isolation через org_id + PostgreSQL RLS

**Дата:** 2026-03-01  
**Статус:** Accepted  
**Авторы:** CAT Team

---

## Контекст

CAT — мультиарендная SaaS-платформа. Данные разных клиентов (брендов) должны быть полностью изолированы. Нужно выбрать модель изоляции.

## Рассматриваемые варианты

| Вариант | Изоляция | Сложность | Скейл |
|---------|----------|-----------|-------|
| Отдельная БД на клиента | Максимальная | Очень высокая (N баз, N миграций) | Ограниченный |
| Отдельная схема (schema) | Высокая | Высокая | Умеренный |
| **org_id в каждой таблице + RLS (выбран)** | Высокая | Умеренная | Хороший |
| Без изоляции (JWT-only) | Низкая | Минимальная | — |

## Решение

**Shared database, shared schema с `org_id` в каждой строке.**

1. Каждая таблица содержит `org_id UUID NOT NULL REFERENCES organizations(id)`
2. Каждый SQL-запрос в репозиторном слое фильтрует `WHERE org_id = :org_id`
3. PostgreSQL Row-Level Security (RLS) как backstop — блокирует запросы без фильтра на уровне БД
4. Возврат `404` (не `403`) для ресурсов чужой org — защита от IDOR-перебора

```python
# Обязательный паттерн в каждом репозитории:
result = await db.execute(
    select(SKU).where(SKU.org_id == org_id, SKU.id == sku_id)
)
```

## Последствия

- **Положительные:** один деплой обслуживает всех клиентов, миграции применяются один раз, JOIN между доменами работают
- **Отрицательные:** пропущенный `org_id` фильтр = утечка данных (RLS — последний рубеж, не единственный)
- **Правило Code Review:** каждый новый запрос без `org_id` фильтра — блокирующий баг (Agent 3 в Phase 4 Review проверяет это явно)
