# ADR-002: Dual Database — PostgreSQL + ClickHouse

**Дата:** 2026-03-01  
**Статус:** Accepted  
**Авторы:** CAT Team

---

## Контекст

CAT собирает данные ежедневно по схеме: N клиентов × M SKU × K платформ × L метрик × 365 дней. Нужно:
1. Хранить транзакционные данные (SKU, пользователи, алерты, планы дистрибуции)
2. Хранить и быстро агрегировать временны́е ряды (цены, остатки, оценки контента)

## Рассматриваемые варианты

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| Только PostgreSQL | Один движок, транзакции | OLAP-запросы по временным рядам медленные при >10M строк |
| Только ClickHouse | Быстрые агрегации | Нет ACID-транзакций, сложные JOIN с мастер-данными |
| TimescaleDB | PostgreSQL-совместим | Медленнее ClickHouse на колоночных агрегациях |
| **PostgreSQL + ClickHouse (выбран)** | Каждый движок оптимален под свою задачу | Два движка → сложность операций |

## Решение

- **PostgreSQL 16** — мастер-данные: org, user, sku, alert, distribution_plan, report. Alembic миграции.
- **ClickHouse** — временны́е ряды: price_snapshots, stock_snapshots, content_scores, review_aggregates. Запись через Celery-воркеры после каждого скрапа.

Данные не дублируются: в ClickHouse хранятся только `sku_id` + метрики, JOIN с мастер-данными делается в API-слое.

## Последствия

- **Положительные:** агрегации по 12 месяцам выполняются за <100ms (ClickHouse columnar); транзакционная целостность SKU/алертов сохранена
- **Отрицательные:** два connection pool, два набора миграций, сложнее локальный dev-setup
- **Правило:** мастер-данные → PostgreSQL, метрики → ClickHouse. Нарушение этого правила требует нового ADR.
